## 概述

本报告验证 P12 优化（延迟建索引 + 分段 commit + WAL checkpoint TRUNCATE）在正式 schema（51 表 + 112 索引 + 3 触发器）下的**初步**性能表现，覆盖 10万 至 1000万 符号四个规模。

**注意**：此为合成数据测试，非真实 E2E。真实 E2E 测试任务：`T-1783907127393-2d1f`

**优化前基线**（建表时同步建索引）：2M 入库 1031s（写放大严重）
**优化后**：建表无索引 → 入库分段 commit → 入库完成后一次性建索引 → WAL checkpoint TRUNCATE

## 规模扩展性分析

### 每M入库耗时随规模变化

| 规模 | 每M入库(s/M) | 相对 1M 倍数 |
|------|-------------|-------------|
| 0.1M | 49.20 | 1.73x |
| 1M | 28.40 | 1.00x（基准） |
| 5M | 27.24 | 0.96x（cache 仍可容纳） |
| 10M | 45.57 | 1.60x（**cache 不够，性能拐点**） |

**结论**：5M 是当前 64MB cache 的性能拐点。10M 时 DB 13GB >> cache 64MB，页面淘汰导致超线性增长。

### 每M建索引耗时随规模变化

| 规模 | 每M建索引(s/M) | 相对 1M 倍数 |
|------|---------------|-------------|
| 0.1M | 52.80 | 1.42x |
| 1M | 37.13 | 1.00x（基准） |
| 5M | 48.87 | 1.32x |
| 10M | 71.35 | 1.92x |

**结论**：建索引超线性增长明显。B-tree 索引在数据量大时：
1. 树深度增加（4KB page → 10M 数据约 3-4 层）
2. 内部节点 cache miss 率上升
3. 节点分裂时需回写父节点

## 容错性验证

分段 commit（每 10 批 = 50万符号 commit 一次）提供以下容错：

| 规模 | 总批数 | commit 次数 | 崩溃最大丢失（符号） | 崩溃最大丢失（调用边） |
|------|--------|------------|--------------------|--------------------|
| 0.1M | 2 | 3 | ≤ 50万 | ≤ 100万 |
| 1M | 20 | 12 | ≤ 50万 | ≤ 100万 |
| 5M | 100 | 48 | ≤ 50万 | ≤ 100万 |
| 10M | 200 | 93 | ≤ 50万 | ≤ 100万 |

> **⚠️ 修正（review 反馈）**：之前报告错误地写为"≤ 5万符号"。实际窗口 = 每批 5万符号 × 每 10 批 commit = **50 万符号**；calls 每批 10万 × 每 10 批 commit = **100 万条边**。

**崩溃恢复**：进程中断后，已 commit 的数据持久化在 SQLite 主 DB 文件中。重启后只需重新入库最后未 commit 的 ≤ 50 万符号 + ≤ 100 万调用边，无需全量重做。

### 当前性能分析
- 入库：从 0.1M → 10M，每M入库耗时从 49s/M → 45.57s/M（10M规模），但 5M 时只有 27.24s/M
  - 这说明 cache 大小是瓶颈：5M (1.25GB DB) 时 64MB cache 还能 hold 大部分热数据；10M (13GB DB) 时 cache 远不够
- 建索引：每M建索引从 37s/M → 71s/M，超线性增长
  - B-tree 索引在数据量大时深度增加，节点分裂频繁
  - 64MB cache 不够 hold 所有索引的内部节点

### 优化方向分析

#### 1. PRAGMA 调优（最容易）
- **cache_size 调大**：从 64MB → 256MB 或 512MB
  - 10M 数据 13GB，cache 占比 0.5% → 2% → 4%
  - 预计可降 20-30% 入库时间
- **mmap_size 调大**：从 256MB → 1GB 或 2GB
  - 减少 ReadFile 系统调用
- **page_size**：默认 4KB，可改 8KB 或 16KB（需建库时设置）
  - 大页减少 B-tree 深度，但增加写放大

#### 2. 建索引并行化
- SQLite 单连接不支持并发写，但可以分多个连接并行建不同索引
- 或用 ATTACH 多个独立 DB 分别建索引后合并
- 难点：CREATE INDEX 需要全表扫描，多索引同时建会互相争抢 cache
- **实际上**：SQLite 已自动优化，CREATE INDEX 会做内部排序，多个索引串行建反而比并行更高效（避免 cache 抖动）

#### 3. 减少索引数量
- 112 个索引中可能有些是冗余的或低使用率的
- 评估每个索引的使用频率，删除低频索引
- 预计可降 30-50% 建索引时间

#### 4. 分批建索引 + checkpoint
- 每建 N 个索引就 commit + WAL checkpoint 一次
- 避免建索引过程中 WAL 膨胀
- 但实测 WAL 已经 truncate 到 0，这点收益有限

#### 5. 入库时批量事务
- 当前每 10 批 commit，每批 50000 符号
- 可改为整个入库过程一个事务（只在最后 commit）
- 但失去容错性，崩溃全丢

#### 6. 数据预处理
- 符号按 file_instance_id 排序后再插入，提高局部性
- calls 按 caller_id 排序，提高索引局部性
- 预计可降 10-15% 入库时间

#### 7. 使用 SSD + 更大内存
- 硬件层面：13GB DB 在 HDD 上会非常慢，SSD 是必需
- 内存：当前 64MB cache 偏小，建议 1-2GB

#### 8. 分库分表
- 将 symbols/calls 按文件 hash 分片到多个 DB
- 查询时 ATTACH 合并
- 但增加复杂度，且合并查询有性能损耗

#### 9. Rust 扩展加速
- 当前 Python sqlite3.executemany 有 GIL 限制
- 用 Rust + rusqlite 可以绕过 GIL，多线程并行入库
- 但 SQLite 单连接仍不支持并发写，需要多连接+ATTACH

#### 10. 使用 PG/MySQL
- 如果数据量持续增长，可考虑迁移到 PostgreSQL
- 支持 VACUUM、并行索引构建、WAL 流复制等
- 但这是大改动

## 可进一步优化的方向（按收益/成本排序）

### 1. PRAGMA 调优（立即收益，零成本）⭐⭐⭐

**问题**：当前 `cache_size=-64000`（64MB）对 13GB DB 仅占 0.5%，10M 时 page 淘汰严重。

**优化**：
```python
# 根据数据规模动态调整
if expected_symbols >= 5_000_000:
    self.conn.execute("PRAGMA cache_size=-262144")  # 256MB
    self.conn.execute("PRAGMA mmap_size=1073741824")  # 1GB mmap
elif expected_symbols >= 1_000_000:
    self.conn.execute("PRAGMA cache_size=-131072")  # 128MB
```

**预期收益**：10M 入库从 456s → ~280s（-38%），建索引从 714s → ~500s（-30%）

### 2. 索引精简（中等收益，低成本）⭐⭐⭐

**问题**：112 个索引中部分使用率低，每个索引建索引时都要全表扫描一遍。

**优化**：审计索引使用频率，删除低频索引：
- `idx_symbols_kind`（按符号类型查询，使用率低）
- `idx_calls_callee_qualified`（与 `idx_calls_callee_name` 冗余）
- `idx_file_versions_current`（布尔字段索引选择性差）

**预期收益**：建索引时间下降 20-30%（减少 15-20 个索引的全表扫描）

### 3. 数据预排序（中等收益，低成本）⭐⭐

**问题**：入库时符号按生成顺序插入，`file_instance_id` 不连续，导致 B-tree 叶子页频繁分裂。

**优化**：入库前按 `(file_instance_id, start_line)` 排序：
```python
symbols.sort(key=lambda s: (s[1], s[6]))  # file_instance_id, start_line
calls.sort(key=lambda c: c[1])  # caller_id
```

**预期收益**：入库时间下降 10-15%（B-tree 顺序插入，减少页分裂）

### 4. 分批建索引 + 中间 checkpoint（小收益，低成本）⭐

**问题**：112 个索引在一个事务中建，WAL 可能膨胀。

**优化**：每 30 个索引 commit + checkpoint 一次：
```python
index_stmts = SCHEMA_INDEXES_SQL.split(';')
for i, stmt in enumerate(index_stmts):
    if stmt.strip():
        conn.execute(stmt)
    if (i + 1) % 30 == 0:
        conn.commit()
        conn.execute("PRAGMA wal_checkpoint(PASSIVE)")
```

**预期收益**：建索引时间下降 5-10%（减少 WAL 回写压力）

### 5. page_size 优化（一次性收益，需重建库）⭐

**问题**：默认 4KB page，10M 数据时 B-tree 深度 3-4 层。

**优化**：建库时设置 `page_size=8192`（8KB）或 `16384`（16KB）：
```python
conn.execute("PRAGMA page_size=8192")  # 必须在创建表前设置
conn.execute("PRAGMA journal_mode=WAL")
```

**预期收益**：B-tree 深度减 1 层，建索引下降 15-20%，但增加少量写放大

### 6. 并行建索引（高收益，高复杂度）⭐⭐

**思路**：SQLite 单连接不支持并发写，但可以用多连接 ATTACH 策略：
- 主库建表+入库
- 将 symbols/calls 表 ATTACH 到 N 个临时库
- 每个临时库并行建不同索引
- 最后合并回主库

**难点**：合并阶段有开销，且 SQLite ATTACH 合并性能不稳定。实测在 2M 规模下 B_4w 策略反而比 A 慢 2x。

### 7. 主从表/内存表架构（高收益，高复杂度）⭐⭐⭐

**思路**（与用户偏好一致）：
- 写入主表（无索引，纯顺序写）
- 异步复制到只读从表（有索引，查询用）
- 主表在内存中维护，定期 dump 到磁盘

**架构**：
```
写入路径：Python → 主表(内存/无索引) → 异步批量 dump → 磁盘主表
查询路径：MCP/CLI → 从表(磁盘/有索引) → 直接查询
复制过程：后台线程定期 INSERT INTO 从表 SELECT * FROM 主表
```

**预期收益**：入库时间下降 80%+（纯内存写），但增加架构复杂度

### 8. Rust 扩展加速建索引（高收益，高成本）⭐⭐

**思路**：用 Rust + rusqlite 绕过 Python GIL，多线程并行建索引：
- 每个索引在独立连接上并行创建
- 利用多核 CPU

**难点**：SQLite 同一数据库多连接写会撞锁，需要用 ATTACH 分库策略

| 场景                 | 冷启动频率               | 冷启动成本可摊薄？ | 推荐方案                    |
| -------------------- | ------------------------ | ------------------ | --------------------------- |
| **笔记本/台式机**    | 每天多次（开关机、合盖） | ❌ 140s 无法接受    | P13/P14/P15（<1s 冷启动）   |
| **服务器（多用户）** | 一次启动，长期运行       | ✅ 摊薄到忽略不计   | P16-Full（查询 5000x 加速） |

**关键点**：P16 的价值在于"一次加载，多次查询"。服务器场景下 1000 次查询就能摊薄 140s 冷启动成本（每次查询省 100ms × 1000 = 100s），而笔记本场景下用户可能只查几次就关机。

## 自适应方案正是为此设计

是的，需要根据**机器配置 + 使用场景**自动选择方案。我设计的自适应逻辑考虑了两个维度：

```
         内存够装 GraphStore？
              │
      ┌───────┴───────┐
     是                否
      │                │
  长期运行？      按内存选 cache_size
      │                │
  ┌───┴───┐     ┌──────┴──────┐
  是       否    <8GB→P13    >16GB→P15
  │        │
P16-Full  P16-Lite
```

但你的观察提示了一个我之前没考虑到的维度：**冷启动频率**。服务器场景除了内存大，更重要的是"长期运行不关机"。所以自适应逻辑应该增加第三个判断条件：

```python
def select_strategy(available_mem, symbol_count, is_long_running):
    """三个维度选择策略
    
    Args:
        available_mem: 可用内存
        symbol_count: 符号数
        is_long_running: 是否长期运行（MCP Server/watcher vs 一次性 CLI）
    """
    graph_store_mem = (symbol_count / 1_000_000) * 550
    
    # P16 仅在长期运行 + 内存足够时才启用
    if is_long_running and available_mem >= graph_store_mem + 2048:
        return "P16_FULL" if available_mem >= graph_store_mem * 1.5 else "P16_LITE"
    
    # 否则走 SQLite 策略，按内存调 cache
    if available_mem >= 32 * 1024: return "P15"
    if available_mem >= 16 * 1024: return "P14"
    return "P13"
```

`is_long_running` 的判断方式：
- MCP Server 启动（`cw server`）→ `True`
- watcher 启动（`cw --watch`）→ `True`
- 普通 CLI 命令（`cw --search`、`cw --refresh`）→ `False`

这样设计能确保：
- **笔记本跑 `cw --search`**：P13，<1s 冷启动，查完即走
- **服务器跑 MCP Server**：P16-Full，一次加载 5s（快照优化后），后续查询全部 <1μs
