# 评审门禁卡（Gate Card）

> 用在三处：R0 需求评审 / G-Tech 选型评审 / R3 设计评审。
> **四件套缺一不过门**。目的：制度化"找优缺点 + 多轮挑战"，从机制上防 happy path。

## 一、四件套

### 1. 方案对比表（≥2 候选）

```markdown
| 维度 | 方案 A（推荐） | 方案 B | 方案 C |
|---|---|---|---|
| 做法 |  |  |  |
| 优点 |  |  |  |
| 缺点 / 代价 |  |  |  |
| 失效模式 |  |  |  |
| 适用条件 |  |  |  |
| 结论 | ✅ 选它，因为… | ❌ 否决（见下） | ❌ 否决（见下） |
```

维度按场景裁剪，但**必须含"失效模式"**——只写优点的对比表等于没做。

### 2. 被否决项及理由

```markdown
- **否决 B**：<具体原因>；在 <什么条件> 下会重新考虑
```

不写 = 门禁不通过。**"没想到别的方案"不构成豁免**，那只说明还没设计。

### 3. 异常场景矩阵（8 类逐一过）

| # | 场景 | 要回答的问题 |
|---|---|---|
| 1 | 空值 / 缺省 | 入参为空、集合为空、字段缺失时走哪条路径？ |
| 2 | 无权限 | 身份不足、越权访问、跨 workspace 时如何拒绝且不泄露信息？ |
| 3 | 重复请求 | 幂等键是什么？重复提交会产生什么副作用？ |
| 4 | 冲突 | 并发写同一资源、版本冲突、状态机非法迁移如何裁决？ |
| 5 | 依赖失败 | 下游超时/报错/返回脏数据时，本层是降级、重试还是失败退出？ |
| 6 | 重试 | 重试次数/退避/上限？重试会不会放大副作用？ |
| 7 | 取消 / 恢复 | 中途取消留下的半成品如何清理？重启后能否续做？ |
| 8 | 数据边界 | 超长、超大、精度、时区、编码、排序稳定性 |

**每类都要落一行结论；"不适用"也是结论**（写清为什么不适用，不是留空）。

### 4. 未决项清单（三态分离）

```markdown
| 类型 | 内容 | 责任人 | 验证方式 / 推翻条件 |
|---|---|---|---|
| confirmed | 用户明确拍板的 | — | 出处（哪轮问答） |
| assumption | 我方假设的 | <谁> | <怎么验证；什么情况下推翻> |
| open | 仍未定的 | <谁> | <何时必须定；不定则阻塞什么> |
```

**不得把推测写成已批准事实**。需求条目带 `REQ-xx` 稳定编号。

## 二、多轮交互协议

1. **复述确认**：产出前先复述一遍理解（"我理解你要做的是……"）。
2. **挑战 → 修订 → 复评**：用户挑战任一件后修订并复评，不辩论。
3. **每门禁 ≤2 轮挑战封顶**；超轮分歧记入 `open`，由用户裁决后继续——**不得悬置阻塞，也不得无限拉扯**。

## 三、hotfix 豁免

三条**同时**满足才可跳过第 1、2 件：

- 单文件改动
- 无新增符号
- 该文件已有测试覆盖

仍须保留异常矩阵 + 未决项，并在 brief 写明三条判据的**逐条核对结果**。任一不满足即回落完整四件套。

> 单文件 ≠ 低风险：改一行权限判断也是单文件。所以豁免锚在"无新增符号 + 有测试兜底"。

## 四、确认摘要（R3 一次性确认时给用户）

```markdown
确认摘要
- 卡片数：<n>（核心 <n> / 叶子 <n>）
- 方案对比：<n> 个候选，否决 <n> 个
- 风险 top3：<...>
- assumptions：<n> 条（其中 parking-lot <n>）
- 本次 scope 快照：must <n> 条 / 指定 should <n> 条
- 待你确认：<一句话问题>
```

只给摘要 + 关键分歧点，不甩整份文档让用户自己找重点。
