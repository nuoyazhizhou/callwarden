# 基线 · 变更 · 证据

> 三个东西一起管，因为它们共用一条时间线：R3 冻结出基线，之后每次改动产生变更单与证据，R5 收口一次性提交并判定关闭。

## 一、工件目录（统一落盘）

`<repo>/.design/<feature>/`，**全部保留 git 跟踪，不写 .gitignore**。

| 工件 | 路径 | 产生 | 提交时点 |
|---|---|---|---|
| brief / 锚定表 / 卡片 / ac-map / task-map / 图 | `<feature>/*.md` | R0-R4 | **R3 基线提交**，之后走追加提交 |
| 验收证据 | `<feature>/evidence/<AC-id>[-r<n>].md` | R5 验收 | **R5 收口提交** |
| 扫描结果 | `<feature>/evidence/scan-<stage>.md`（注释 / orphan / coverage / guardrail） | R5 收口 | 同上 |
| 变更记录 | `<feature>/change-log.md`（**只追加**） | 每次变更单 | **每次变更单一次提交** |
| 停车场汇总 | `.design/parking-lot.md`（跨 feature，**只追加**） | R0 | 随所在 feature 的基线/收口提交 |

### 提交纪律

1. 设计/证据提交是**独立提交**，不与源码任务提交混合——hunk 级纪律只约束源码。
2. 提交时点只有三个：**R3 基线 / 每次变更单 / R5 收口**。不逐步零散提交。
3. 基线提交范围限定 `.design/<feature>/`；`.design/parking-lot.md` 可随同一次提交。

> 为什么强调"独立提交"：一旦证据文件混进源码提交，hunk 级审查（只允许改白名单文件）会拒，或者审查者被迫在业务 diff 里读日志。

## 二、基线冻结（R3 确认后，三件事）

1. `git commit .design/<feature>/` —— 独立"设计基线提交"。
2. **记录 HEAD commit** 写入 `requirements-brief.md`（R5 漂移检查的参照）。
3. **定义 scope 快照**：must + 指定 should；其余标 `deferred`。

快照一个定义、三处使用：

- R4 建单范围（首批只 must）
- R5 关闭判据（快照内 AC 全绿才算关闭）
- deferred 条目归属（快照外，转下批，不阻塞关闭）

## 三、变更单程序（基线之后）

### 卡片变更

1. 卡片 `revision + 1`
2. 关联任务留言说明差异
3. 重跑该卡 `check_items`
4. 已建任务未闭环 → 留言 + 重跑；已闭环 → 按 REQ 新建整改单

### REQ 变更

1. `REQ-xx` revision + 1
2. **须用户确认**（业务变更，不是技术决定）
3. 沿 `task-map.md` 反查受影响 AC / 卡片 / 任务
4. 同步修订 `ac-map.md`（验收方式可能一起变）

### 升级条件

受影响卡 **> 3 张**（可调）→ 升级完整重规划（交 planner / 记 capability gap），不再逐卡打补丁。

### 记录格式（`change-log.md`，只追加）

```markdown
## 2026-11-22 · CT-03
- 类型：设计变更 / REQ 变更 / 卡片缺陷
- 对象：REQ-03 r2 → 卡片 publish_capture r2 → T-xxx
- 原因：<触发事实，不是猜测>
- 影响面：AC-05 验收方式变更；2 张卡受影响
- 批准人：<用户 / 角色>
- 提交：<基线 HEAD> → <本次 commit>
```

**只追加不改写历史**。历史错了就再写一条更正，不回头编辑。

## 四、证据

### 落盘要求

- 写**结论 + 关键输出**（执行命令、断言、可观察行为），不贴全量日志。
- **不得含密钥 / token / 个人数据**；输出须脱敏。
- 二进制证据（截图 / 日志包）允许，但须在同名 `.md` 里写明来源、取得方式、判读结论——否则后人无法判断这张图证明了什么。

### 缺失即失败

`ac-map.md` 的"证据位置"为空，或指向不存在的文件 = **该 AC 未通过**。不得口头声明通过。

这条是 fail-closed 的：验收的产物是证据，不是"我说跑过了"。

## 五、关闭判据

- **快照内** REQ→AC 全绿 + 证据齐备且已提交 → 需求关闭
- **快照外** 条目：标 `deferred`，记录下批归属，**不阻塞关闭、也不假装已完成**
- 扫描/验收发现的整改单：首行带 `REQ-xx`；无对应 REQ 记 `REQ-GAP` 并归类，**不得无编号建单**
