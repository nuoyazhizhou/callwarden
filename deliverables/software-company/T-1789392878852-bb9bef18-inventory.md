## 1. 缺陷现场（本 HEAD 逐行复核，非照抄 backlog 行号）

落点：`rust_ext/src/daemon/admin_handlers.rs`

- `handle_gc_audit_get`（L129-162）：L138 SQL
  `... FROM change_audit WHERE id = ?1 AND task_id IN (SELECT id FROM tasks WHERE workspace_id = ?2) LIMIT 1`
  —— 子查询引用 `tasks.workspace_id`（不存在列）。
- `handle_gc_audit_list`（L165-193）：L173-176 SQL
  `... FROM change_audit ca JOIN tasks t ON t.id = ca.task_id WHERE t.workspace_id = ?1 ...`
  —— JOIN 后 WHERE 引用 `t.workspace_id`（不存在列）。

两 handler 的 `workspace_id: i64` 参数由路由层传入；C-17（`186582e`）已把 admin 路由块
作用域从 registry 代理 ROWID 收敛为物理库 `workspaces.id`（经 `open_codegraph_db_write`
按 `client_view_root` 规范化匹配 `root_path` 取真 id）。即：**路由传入值已正确，故障仅在
handler SQL 引用了 tasks 表上不存在的列** → 恒 `prepare` 失败。

## 6. 修法定型

两 handler 改经权威 binding 表作用域（签名/返回结构/参数校验不变；路由层零触碰）：

- `gc_audit_get`：`... WHERE id = ?1 AND task_id IN
  (SELECT task_id FROM task_workspace_bindings WHERE workspace_id = ?2) LIMIT 1`
- `gc_audit_list`：`... FROM change_audit ca JOIN task_workspace_bindings b
  ON b.task_id = ca.task_id WHERE b.workspace_id = ?1 ORDER BY ca.timestamp DESC LIMIT ?2`

语义与 `task_bound_workspace_id` 同源：unbound task 的 change_audit 行不归属任何
workspace，天然不可见（fail-closed 语义在只读面的自然延伸）。
