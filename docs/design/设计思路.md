### Rust daemon 怎么使用

Rust 不硬编码整篇文本，只负责加载嵌入资源：

```rust
const EXECUTOR_TEMPLATE: &str =
    include_str!("../../resources/role_prompts/v1/executor.md");
```

运行时：

1. `task.next_action` 判定当前角色和动作。
2. `task.prompt_context` 聚合权威数据。
3. `task.prompt_render` 选择正确模板。
4. Rust 填充任务变量。
5. 返回 `prompt_text`、模板 hash 和 bundle hash。

这样模板仍然是便于审查和修改的 Markdown，但运行时使用的是 daemon 二进制中不可漂移的副本。

### 为什么不放客户端

如果模板跟 CLI/MCP 客户端放在一起，会产生几个问题：

- 不同 Agent 安装了不同客户端版本；
- Reviewer 与 Executor 可能得到不同治理规则；
- 客户端可以改写 allowed paths、路由或 Handoff；
- Python 客户端重新拥有治理业务逻辑；
- 远端 Agent、Codex、Kiro、Claude 可能生成不同提示词。

这与“Python 只做 HTTP thin client”的目标冲突。

客户端只保留这样的薄入口：

```python
result = daemon.call("task.prompt_render", {"task_id": task_id})
print(result["prompt_text"])
```

MCP 同样只透传。

### 为什么不放普通 daemon 配置文件

普通 YAML/TOML 配置适合端口、日志级别，不适合治理提示词。否则本地改一行配置就可能改变角色权限和审查规则。

默认生产路径应为：

```text
版本控制的模板文件
    → 校验
    → 编译嵌入 daemon
    → template hash
    → prompt bundle hash
```

配置文件最多允许调整：

- 输出语言；
- 是否包含详细命令；
- 显示详细程度；
- 本地 CLI 路径的展示形式。

配置不能调整：

- 角色权限；
- allowed/excluded paths；
- outcome 路由；
- lease 要求；
- Handoff 字段；
- PASS/BLOCKED/apply/close 门禁。

- 从聊天猜测的 identity
- 未持久化的 verdict/handoff

这些由 Agent runner 在执行命令时，通过本机受保护的 session store 注入。提示词只写“需要哪种身份和 lease”。

### 最终用户体验

以后用户不需要说：

```text
你是 Reviewer，请读这些文件，然后检查……
```

只需要：

```text
处理 T-1787310376068-44eb5f20
```

后台执行器自动完成：

```text
task_id
  → 生成 Executor prompt
  → Executor report
  → 生成 Reviewer prompt
  → Reviewer verdict
  → 生成 Adjudicator prompt
  → apply/close
```

如果任务需要重规划：

```text
task_id
  → Planner prompt
  → 新 Contract/任务拆分
  → Executor prompt
```

如果存在真正需要用户选择的路线，才生成 `decision_request`，在类似 Jira 的控制台里让用户选择，而不是让 Agent 在聊天窗口输出一大段“请用户处理”。

所以整体定位可以概括为：

> **Task Contract 提供内容，daemon 决定角色，角色模板提供工作方法，Prompt Compiler 把它们组装成可审计的 LLM 执行上下文。**

>你的意思这个思路完成以后我不用告诉 agent ，你是谁，你要做什么， 直接给一个taskid 或者直接说 请处理 xxx，然后 agent 自动从 cw 拉取 task 的状态信息，然后根据状态 分配给不同的角色提示词，然后返回，对吗

对。实现完成后，你不需要再手工告诉 Agent：

- 你是 Planner、Executor、Reviewer 还是 Adjudicator；
- 应读取哪些文档；
- 应执行哪些步骤；
- 应交给哪个角色；
- Handoff 应该怎么写。

你只需要输入：

```text
请处理 T-1787310376068-44eb5f20
```

系统自动完成：

```text
task_id
  ↓
从 daemon 读取任务、Contract、binding、step、verdict、finding、状态
  ↓
task.next_action 判断当前需要哪个角色
  ↓
生成该角色的 prompt bundle
  ↓
派发给对应的已注册 Role Worker
```

例如：

```text
READY/PLAN        → 独立 Planner worker
READY/CLAIM       → Executor worker
READY/REVISE      → Executor remediation worker
READY/REVIEW      → 独立 Reviewer worker
READY/ADJUDICATE  → 独立 Adjudicator worker
BLOCKED           → 生成当前责任角色的恢复提示词
COMPLETE          → 返回完成确认
```

每一棒完成后，系统用同一个 `task_id` 重新查询：

```text
Executor report
    ↓
重新 task.next_action
    ↓
自动启动独立 Reviewer session
    ↓
Reviewer PASS
    ↓
重新 task.next_action
    ↓
自动启动独立 Adjudicator session
    ↓
apply → close
```

有一点很重要：这不是同一个 Agent 在同一窗口里随意切换角色。前台入口只是无决策权的调度器，真正工作由不同的注册 worker 和独立 session 执行：

```text
用户
  ↓
无角色调度入口
  ├─ Planner worker/session
  ├─ Executor worker/session
  ├─ Reviewer worker/session
  └─ Adjudicator worker/session
```

身份、session 和凭据也不需要你填写：

- daemon 根据 `required_role` 选择已注册 worker；
- runner 创建该角色的新 session；
- 本机受保护 session store 注入 credential；
- lease token 只在进程内传递；
- prompt 中不出现秘密。

如果没有可用的对应 worker，系统应显示：

```text
任务：T-...
当前需要：reviewer
状态：waiting_for_worker
原因：没有 active reviewer worker
```

而不是让你自己编写 Reviewer 提示词。

如果你说：

```text
请处理 P0-F
```

系统可以先搜索任务；只有找到多个同名任务时才让你选择。提供精确 `task_id` 时可以直接执行。

但这是目标能力，目前还没有完整实现。当前 `cw-task-loop` 只能查询 `next-action` 并生成较短的角色卡，还缺少：

- Rust `task.prompt_context`
- Rust `task.prompt_render`
- 版本化角色模板
- `cw task prompt`
- MCP `task_get_role_prompt`
- worker 自动分派和新 session 创建
- prompt bundle hash 与 report/verdict 绑定

这些完成后，你与系统的日常交互就可以简化为一句：

```text
请处理 T-xxxxxxxx
```

只有遇到真正的业务选择、外部资料、验收或敏感授权时，系统才会回来找你。



建议采用中间路线：

> 先把已经接近闭环的 P0-B～P0-F 完成，然后立刻实现“Task → 角色提示词”能力；不要等 P0-L 的 11 个子任务全部完成，更不要等整个 Epic 完成。

| 任务 | 当前阶段 |
|---|---|
| P0-B | `adjudication_pending` |
| P0-C | `adjudication_pending` |
| P0-D | `adjudication_pending` |

随后分两阶段实现新能力。

### 第一阶段：立即实现 Prompt Compiler

不等 P0-L 11 个任务，先实现只读能力：

```text
task_id
  → task.next_action
  → task.prompt_context
  → task.prompt_render
  → 返回当前角色完整提示词
```

建议拆成四张小卡：

1. `RP-0`：`role_prompt_v1` schema、模板变量、版本/hash/失效规则。
2. `RP-1`：Rust `task.prompt_context`，聚合任务、Contract、binding、step、report、verdict。
3. `RP-2`：Rust `task.prompt_render` 与版本化 Planner/Executor/Reviewer/Adjudicator 模板。
4. `RP-3`：薄 CLI/MCP、`cw-task-loop` 接入、四角色和秘密泄漏测试。

这一阶段是只读的，不取得 lease、不自动 claim、不执行 mutation，所以不依赖全部 P0-L Role Worker 能力。

完成后，P0-L 的 11 个任务就可以用它执行：

```text
请处理 T-...
```

系统自动生成当前 Executor、Reviewer 或 Adjudicator 的提示词，马上降低后续 11 张卡的沟通成本。

### 第二阶段：实现无人值守自动派发

这一阶段才依赖 P0-L 中的：

- Role Worker session 生命周期；
- identity policy；
- credential/session store；
- lease acquisition/proof；
- stale recovery；
- `next_action` 投影一致性；
- CLI/MCP role-session surface。

它负责：

```text
生成提示词
  → 找到对应 Role Worker
  → 创建独立 session
  → 投递 prompt bundle
  → 执行动作
  → handoff 后自动启动下一角色
```

所以完整顺序应为：

```text
1. P0-B～P0-F review/adjudication/apply/close
2. 实现只读 role_prompt_v1 Prompt Compiler
3. 用 Prompt Compiler 推进 P0-L 11 个子任务
4. P0-L 的 worker/session/lease 能力完成后，实现自动派发 runner
5. 用完整自动 loop 推进 A0～A6 和 Python authority 下沉
```

不建议等 11 个子任务都完成后再做，因为那会继续让 11 个任务依赖人工复制提示词；也不建议现在立刻改 daemon，因为 P0-B～P0-F 的最终运行时证据正在收尾。

因此眼前唯一顺序是：**先让 Reviewer/Adjudicator 关闭 P0-B～P0-F，然后 Prompt Compiler 成为下一条优先主线。**
