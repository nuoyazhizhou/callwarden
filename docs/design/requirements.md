# Requirements Document

## 多 LLM 契约驱动协同需求

> **状态**：目标需求（分阶段落地，非当前已实现能力声明）  
> **Feature**：`multi-llm-contract-collaboration`  
> **工作流**：Design-first  
> **设计依据**：`multi-llm-contract-driven-collaboration-design.md`

## Introduction

本文从已批准的目标设计推导多 LLM 契约驱动协同需求。P0 是不修改 schema 的对照实验；P1 至 P4 是依次启用的产品化阶段。除明确标记为现有状态机兼容行为的条目外，本文描述的是待实现和待验证的目标能力，不表示 Call Warden 当前已经具备对应能力。

本文的协同能力以 daemon 为唯一串行化点与权威时钟（Requirement 14）。原始驱动动机是多 Agent 会话并行工作时出现的 SQLite 锁竞争与"串行接力"，因此 Requirement 14 同时承载跨平台 daemon 化与并行协作验收。

**已作出的决策**：

1. **Windows 传输方式定为命名管道**：Daemon_Endpoint 在 Windows 上是按用户 SID 隔离的命名管道（`\\.\pipe\callwarden-<user-sid>` 形式），以安全描述符仅授权 owner SID（可选 administrators），等价于 Unix domain socket 的 owner + 0660 语义；Daemon 维持多个管道实例并在 accept 后立即补建，使 accept 之间不存在客户端无法连接的竞态窗口。localhost TCP、本机 HTTPS 端点与 Windows 上的 AF_UNIX 均被排除，因为操作系统不为这些连接提供对端身份，Requirement 14.5 无法成立（见 Requirement 14.2、14.18–14.21）。
2. **Daemon 不可用时采用"先唤起 + 按操作分级"**：客户端连不上端点时先尝试启动 Daemon 并在有界等待窗口内退避重试，成功后继续原请求；跨进程互斥保证同一用户端点只有一个 Daemon 进程，不产生第二个 Protected_Mutation 串行化点。唤起失败后按操作分级：只读查询与 Index_Write 允许直连 SQLite 降级执行，Governance_Write 一律 fail closed 并返回带稳定错误码、i18n key 与恢复指引的 Structured_Reason（见 Requirement 14.22–14.33）。降级产物因缺少 Daemon 签发的有效 Attestation 而不能满足任何 Blocking_Clause（Requirements 10.8、10.9、14.13、14.31），因此系统无需物理阻止直连写库。据此，P4 Lease 的定位是"Daemon 在线期间的并发正确性保证"，防篡改保证归属于 Attestation 与追加式 Evidence_Ledger（Requirement 14.32）。
3. **HTTP MVP 是版本化的开发期例外，不是端点安全决策反转**：`http-mvp-transport-profile/v1` 仅在显式选择 `dev_loopback_unauthenticated` 时允许动态 loopback HTTP/JSON-RPC。它是 Requirement 14.20 “无监听 TCP”的唯一例外，不满足 Requirement 14.5 的 OS Peer_Credential，不提供跨用户 ACL、远程授权或生产安全。HTTP 模式下客户端对所有 operation class 均不得使用 Requirements 14.28–14.29 的 SQLite 降级；默认 Named Pipe/UDS 与企业安全口径保持不变（见 Requirements 14.40–14.48）。

**当前实现基线（用于对照，不构成能力声明）**：`rust_ext/src/daemon/server.rs` 标注 `#![cfg(unix)]`，Windows 上不编译、daemon 不启动；`rust_ext/src/daemon/peercred.rs` 仅实现 Linux `SO_PEERCRED` 与 macOS `LOCAL_PEERCRED`（macOS 无 pid 字段），`peercred_is_available()` 在 Windows 返回 false；`rust_ext/src/daemon/workspace.rs` 的 `_validate_owned_path` 在非 Unix 平台跳过 UID ACL 检查（注释标注为开发测试用途）；SCM_RIGHTS FD 传输仅 Unix 可用，Windows 需走既有 `canonical_bytes_b64` 参数路径；`server/daemon_client.py` 已具备 daemon 不可用时的只读 SQL 直连回退路径（`_sql_fallback_*` 方法与 `sql_fallbacks` 计数），Requirement 14.28 的降级只读执行以该路径为基线，而 Index_Write 与 Governance_Write 的分级行为、Degraded_Mode 标记与自动唤起均尚未实现。Requirement 14 描述的是需要补齐的目标能力。

## Glossary

- **协同系统（Collaboration_System）**：实现多 Agent 契约协同、角色投影、判定、证据和门禁的目标系统。
- **任务（Task）**：Call Warden 状态机管理的工作单元。
- **Envelope**：一个任务在指定 revision 下的完整规范协议，是角色间唯一的契约真相源。
- **Canonical_Envelope**：按规定字符编码、字段顺序、路径格式和数组规则规范化后的 Envelope 表示。
- **Envelope_Parser**：把序列化 Envelope 转换为结构化 Envelope 的目标组件。
- **Envelope_Printer**：把结构化 Envelope 输出为 Canonical_Envelope 的目标组件。
- **Revision**：同一 contract_id 下单调递增的契约版本号。
- **Contract_Hash**：排除 hash 自身和纯展示字段后，根据 Canonical_Envelope 计算的内容摘要。
- **Current_Envelope**：Gate 评估时任务已发布的最高有效 Revision 及 Contract_Hash。
- **Role_View**：从同一 Envelope 生成、包含角色履责所需最小字段的只读投影。
- **View_Manifest**：记录 Role_View 类型、版本、Contract_Hash、披露字段和内容摘要的清单。
- **Implementer_Notes**：实现者提交的结构化说明，包括实际改动、契约偏离、未验证事项和建议验证。
- **Blind_First_Pass_Verdict**：Reviewer 在 Implementer_Notes 和既有 verdict 揭示前提交并封存的首轮判定。
- **Reveal_Event**：Blind_First_Pass_Verdict 封存后向 Reviewer 披露 Implementer_Notes 的追加事件。
- **Post_Reveal_Amendment**：Reveal_Event 后关联首轮 verdict 的追加修订。
- **Session**：具有可记录 session_id 的一次 Agent 工作会话。
- **Independent_Review**：Reviewer Session 与 Implementer Session 不同且满足阶段身份规则的审核。
- **独立审核政策（Independence_Policy）**：解析某任务"是否要求 Independent_Review"的政策，取值至少包含默认的 `required` 与非默认的 `solo`。`required` 时该 profile 按 Profile_Policy_Matrix 要求 Independent_Review；`solo` 时该 profile 不再要求 Independent_Review，因此 Requirement 1.5 的前件为假。Independence_Policy 只作用于"是否要求"，不改变"未证明的独立性能否满足条款"（Requirement 5.2 不变）。
- **Verifier 撤销记录（Verifier_Revocation_Record）**：Verifier_Registry 条目 trust_status 变为 `revoked` 时追加的单条不可变记录，承载 Verifier 三元组 `(name, version, config_hash)`、撤销原因、发起者身份与按 Authoritative_Clock 记录的撤销时间；Evidence 的 `invalid` 由该记录在查询时派生，而非逐条写入失效事件。
- **Evidence**：verifier 针对指定契约和代码快照产生的不可变事实记录。
- **Evidence_Ledger**：保存 Evidence、失效事件、verdict 和 gate decision 的追加式逻辑账本。
- **Workspace_Snapshot**：至少由 HEAD、dirty diff 及相关 tracked/untracked 文件内容摘要构成的规范化工作区身份。
- **Gate_Snapshot**：一次 Gate 判定使用的 Workspace_Snapshot。
- **Freshness_Status**：Evidence 的 `fresh`、`stale`、`invalid`、`superseded` 或 `historical_unbound` 派生状态。
- **Verifier**：具有名称、版本和配置摘要的确定性验证器。
- **Verifier_Registry**：登记 Verifier 名称、版本、config_hash 与信任状态的注册表，是"可信 Verifier"的唯一真相源。
- **Blocking_Clause**：severity 为 block 的验收条款。
- **Evidence_Gate**：依据 Current_Envelope、Gate_Snapshot、Evidence 和 verdict 决定状态转换的目标组件。
- **Completion_Gate**：接入 `task_report_step` 的步骤级门禁。
- **Apply_Gate**：接入 `task_apply` 的最终主门禁。
- **Allowed_Edit_Scope**：由 task step 的 target_file/target_symbol 聚合到 Envelope 的允许文件和符号集合。
- **Actual_Changes**：根据磁盘 diff、文件摘要和符号变化得到的变更事实。
- **Reopen**：通过现有 `task_reopen` 语义把 `review`、`applied` 或 `closed` 任务恢复到 `in_progress` 的动作。
- **Hard_Dependency_Graph**：P2 中由 requires_artifact 及可解析的 requires_interface 到 provides_interface 关系形成的有向图。
- **Identity**：P3 中由 agent_id、session_id、model_id 和 role 构成的动作主体标识。
- **Lease**：P4 中包含 token、有效期和 fencing counter 的限时角色授权。
- **Fencing_Counter**：每次新 Lease 单调递增、用于拒绝旧持有者 protected mutation 的序号。
- **Protected_Mutation**：受角色授权与 Evidence_Gate 约束的任务写操作；P4 启用后额外受 Lease 与 Fencing_Counter 约束。
- **治理类写操作（Governance_Write）**：承载授权语义的写操作全集，等同 Protected_Mutation 全集，包括 Envelope 发布、verdict 封存、Reveal_Event 追加、Evidence 追加、gate decision 提交、`task_apply`、`task_close` 以及 Lease 获取、续租与释放。
- **索引类写操作（Index_Write）**：可由当前代码与工作区状态重算的派生事实写入，包括文件刷新、解析结果、符号图更新与图刷新版本记录，不承载授权语义。
- **跨类操作（Mixed_Class_Operation）**：单个用户可见入口同时包含 Index_Write 组成部分与 Governance_Write 组成部分的操作；分级判定以组成部分为粒度，而非以整个入口为粒度。`task_report_step` 是已知实例。
- **降级模式（Degraded_Mode）**：Daemon 自动唤起在有界等待窗口内未成功后，客户端以直连 SQLite 方式执行被允许操作类别的运行模式。
- **Experiment_Evaluator**：执行 P0 分组、样本有效性判定、指标计算和停止判定的实验评估组件。
- **Control**：P0 中 Reviewer 在首轮 verdict 前可见 Implementer_Notes 的对照组。
- **Treatment**：P0 中 Reviewer 在首轮 verdict 封存前不可见 Implementer_Notes 的实验组。
- **Profile**：定义 Envelope 必填字段、默认角色和门禁政策的任务类型。
- **Profile_Policy_Matrix**：为每个 Profile 声明必需 verdict 种类与是否要求 Independent_Review 的可判定映射表。
- **Daemon**：常驻进程，提供协同 RPC、Protected_Mutation 串行化点与权威时钟。
- **Daemon_Endpoint**：Daemon 的本机传输端点，Linux 与 macOS 为 owner 独占、0660 模式的 Unix domain socket，Windows 为按用户 SID 命名、仅授权 owner SID 的命名管道；不包含 TCP 端口、本机 HTTPS 端点与 Windows AF_UNIX。
- **MVP_Transport_Profile**：对默认 Daemon_Endpoint 规则的版本化、显式 opt-in 开发 overlay。当前唯一值为 `http-mvp-transport-profile/v1:dev_loopback_unauthenticated`；只允许动态 IP loopback HTTP/JSON-RPC，不产生 OS Peer_Credential 或生产安全声明。
- **Peer_Credential**：由操作系统内核提供的连接对端凭证，Unix 为 UID/GID（Linux `SO_PEERCRED`、macOS `LOCAL_PEERCRED`），Windows 为命名管道对端访问令牌 SID。
- **Peer_Identity**：仅由 Peer_Credential 派生的对端身份，不含客户端自报字段。
- **Authoritative_Clock**：Daemon 进程时钟，是 Lease 过期、verdict/reveal 顺序与 Evidence 产生时间的唯一权威时间源。
- **Attestation**：由 Daemon 基于 Peer_Credential 与 Authoritative_Clock 签发、绑定 verdict 或 Evidence 的可验证凭证。
- **撤销模式（Revocation_Mode）**：Attestation_Revocation_Record 的必填字段，取值为 `compromised` 或 `rotated`，决定派生时是否比较 Attestation 签发时间。`compromised` 表示签名密钥被泄露，无法区分真实签发与伪造签发；`rotated` 表示例行密钥轮换，轮换时间之前的签发仍可信。该字段没有默认值。
- **Attestation 撤销记录（Attestation_Revocation_Record）**：Attestation issuer 或签名密钥被撤销时追加的单条不可变记录，承载 issuer 标识、签名密钥标识、Revocation_Mode、撤销原因、发起者身份与按 Authoritative_Clock 记录的撤销时间；受影响 verdict 与 Evidence 的 `invalid` 由该记录在查询时派生，而非逐条写入失效事件。派生语义随 Revocation_Mode 分为两种：`compromised` 时忽略 Attestation 签发时间、该 issuer/key 签发的全部记录判为 `invalid`；`rotated` 时仅签发时间晚于撤销时间的记录判为 `invalid`，签发时间早于或等于撤销时间的记录保持原有有效性判定。
- **Stage_Toggle**：P0 至 P4 各阶段的启用开关，具有全局、workspace 与 task 三级作用域。
- **实验批次配置（Experiment_Batch_Config）**：P0 实验工具链自身的本地文件配置，属 Requirement 12.1 允许的无 schema 变更文件记录；在 Daemon 配置存储不可用期间承载 P0 的 Stage_Toggle。
- **Structured_Reason**：包含稳定错误码与 i18n message key 的结构化失败原因。
- **结构化警告（Structured_Warning）**：包含稳定警告码与 i18n message key 的结构化提示。与 Structured_Reason 的区别是 Structured_Warning 非阻断，不改变操作的接受或拒绝语义，仅向调用方与 CLI 输出附加提示。
- **Minimal_Blind_View**：P0 阶段仅由现有字段构成的盲评视图及其披露清单，属实验记录，不是 View_Manifest。
- **P0**：不修改 schema 的 blind-review 对照实验阶段。
- **P1**：Envelope、Role_View、Evidence_Ledger 和 Evidence_Gate 产品化阶段。
- **P2**：artifact/interface 依赖和环检测产品化阶段。
- **P3**：Identity 与独立审核证明产品化阶段。
- **P4**：assignment 和安全 Lease 产品化阶段。


## Requirements

### Requirement 1: 核心正确性不变量

**User Story:** 作为审核与发布责任人，我希望所有硬门禁遵守统一且可验证的不变量，以便错误契约、过期证据或不独立判定无法推动任务状态。

#### Acceptance Criteria

1. WHEN a verdict or Evidence is evaluated for the Current_Envelope, THE Collaboration_System SHALL allow the verdict or Evidence to satisfy a clause only when contract_id, Revision, and Contract_Hash are all present and exactly match the Current_Envelope; otherwise the applicable gate shall fail closed, return a structured binding reason, and preserve the pre-request task and step states.
2. WHEN Evidence is evaluated against a Gate_Snapshot, THE Evidence_Gate SHALL classify the Evidence as fresh only when the Workspace_Snapshot and every relevant file hash and symbol hash exactly match the Gate_Snapshot.
3. WHEN `test_pass` is evaluated for a Current_Envelope and Gate_Snapshot, THE Evidence_Gate SHALL return true if and only if a uniquely identified passed test run covers every required selector, exactly binds the Current_Envelope and Gate_Snapshot, uses an accepted Verifier version and configuration, and has no relevant file or symbol change after test completion.
4. WHEN a Blind_First_Pass_Verdict is submitted, THE Collaboration_System SHALL accept the Blind_First_Pass_Verdict only when submission precedes the Reveal_Event and the View_Manifest contains no Implementer_Notes, prior reviewer verdict, reviewer draft, or hidden reasoning history.
5. WHERE a task profile requires Independent_Review, WHEN `task_apply` is requested, THE Apply_Gate SHALL reject the request unless the Reviewer Session is proven different from the Implementer Session, return a structured independence reason, and preserve the pre-request task state.
6. WHEN Actual_Changes outside Allowed_Edit_Scope are detected, THE Collaboration_System SHALL make the Completion_Gate or Apply_Gate fail closed with a structured scope reason before any requested completion or apply transition changes state.
7. WHEN Evidence, a Post_Reveal_Amendment, or an invalidation event is recorded, THE Evidence_Ledger SHALL append a new record without updating or deleting any original Evidence or verdict payload and shall preserve every original payload byte-for-byte.
8. WHEN any Blocking_Clause has a decision or Freshness_Status of `unsatisfied`, `unknown`, `stale`, or `invalid`, THE Apply_Gate SHALL fail closed, return a structured per-clause reason, and preserve the pre-request task state outside `applied`.
9. WHEN a failed or reopened task receives a new Revision and new Gate_Snapshot-bound Evidence, THE Evidence_Gate SHALL evaluate the new records while retaining every prior failure, verdict, and Evidence record for audit.
10. WHERE P2 is enabled, WHEN an Envelope publication or update changes the Hard_Dependency_Graph, THE Collaboration_System SHALL accept the Revision only when the resulting Hard_Dependency_Graph is acyclic.
11. WHERE P4 is enabled, WHEN a new Lease with fencing counter N is issued for a task and role, THE Collaboration_System SHALL reject every protected mutation for the same task and role carrying a fencing counter lower than N with a structured fencing reason and without changing task data.
12. WHEN any parser, publication, verdict, Evidence, gate, Lease, or Daemon operation returns a Structured_Reason, THE Collaboration_System SHALL include one stable error code from the published error-code catalog and one i18n message key resolvable in both the `zh_CN` and `en_US` catalogs, and SHALL keep the error code stable across message text changes.

### Requirement 2: P1 版本化 Canonical Envelope

**User Story:** 作为 Planner，我希望所有角色使用同一份版本化且可哈希的 Envelope，以便契约语义可复现、可比较并可审计。

#### Acceptance Criteria

1. WHERE P1 is enabled, WHEN a valid serialized Envelope is provided, THE Envelope_Parser SHALL produce a structured Envelope conforming to the selected profile.
2. WHERE P1 is enabled, IF a serialized Envelope violates the Envelope grammar or selected profile, THEN THE Envelope_Parser SHALL return a structured error identifying the invalid field or grammar location.
3. WHERE P1 is enabled, WHEN a structured Envelope is printed, THE Envelope_Printer SHALL emit UTF-8 Canonical_Envelope content with deterministic field ordering, normalized paths, and deterministic array ordering rules.
4. WHERE P1 is enabled, WHEN any valid structured Envelope is printed, parsed, printed, and parsed, THE Collaboration_System SHALL produce two semantically equivalent structured Envelope values and two identical canonical byte sequences.
5. WHERE P1 is enabled, WHEN field order or pure presentation formatting changes without a semantic field change, THE Collaboration_System SHALL preserve the Contract_Hash.
6. WHERE P1 is enabled, WHEN objective, non-goals, interfaces, Allowed_Edit_Scope, acceptance clauses, risks, rollback, or dependencies change, THE Collaboration_System SHALL publish a higher Revision with a recomputed Contract_Hash.
7. WHERE P1 is enabled, WHEN a Revision is published for an existing contract_id, THE Collaboration_System SHALL require the Revision number to be greater than every previously published Revision for the contract_id.
8. WHERE P1 is enabled, WHEN Contract_Hash is computed, THE Collaboration_System SHALL exclude Contract_Hash itself and profile-defined pure presentation fields from the hash input.
9. WHERE P1 is enabled, IF a record has an unchanged Revision with a different Contract_Hash or an unchanged Contract_Hash with an invalid Revision relation, THEN THE Evidence_Gate SHALL classify the record as invalid and block clause satisfaction.
10. WHERE P1 is enabled, IF an executable clause is missing clause_id, subject, operator, expected value, Verifier identity, freshness rule, or severity, THEN THE Collaboration_System SHALL reject publication of the executable clause.
11. WHERE P1 is enabled, IF a clause lacks a stable Verifier or freshness rule, THEN THE Collaboration_System SHALL classify the clause as declarative and exclude the clause from automatic PASS generation.

### Requirement 3: P1 角色最小视图

**User Story:** 作为协同参与者，我希望每个角色仅获得完成职责所需的契约事实，以便减少叙事锚定、信息泄露和投影漂移。

#### Acceptance Criteria

1. WHERE P1 is enabled, WHEN a Role_View is generated, THE Collaboration_System SHALL derive the Role_View from one Envelope and include view_type, view_version, Contract_Hash, and View_Manifest hash.
2. WHERE P1 is enabled, WHEN a Planner Role_View is generated, THE Collaboration_System SHALL include objective, non-goals, existing interface and symbol facts, constraints, dependencies, risks, and declared unknowns.
3. WHERE P1 is enabled, WHEN an Implementer Role_View is generated, THE Collaboration_System SHALL include execution-relevant Envelope fields, target source, interfaces, dependencies, acceptance clauses, risks, rollback, target_file, target_symbol, Allowed_Edit_Scope, callers/callees summaries, and applicable project rules.
4. WHERE P1 is enabled, WHEN a Reviewer first-pass Role_View is generated, THE Collaboration_System SHALL include the Current_Envelope, current Actual_Changes, symbol and signature changes, current-snapshot test/static Evidence, required source and call facts, and Freshness_Status.
5. WHERE P1 is enabled, WHEN a Tester first-pass Role_View is generated, THE Collaboration_System SHALL include executable clauses, affected files, affected symbols, affected interfaces, current Workspace_Snapshot identity, required test selectors, risks, rollback verification, and available test Evidence.
6. WHERE P1 is enabled, WHEN a Reviewer or Tester first-pass Role_View is generated, THE Collaboration_System SHALL recursively omit hidden reasoning history and every prohibited field from top-level fields, nested objects, metadata, summaries, and artifact references for the selected role and disclosure phase.
7. WHERE P1 is enabled, WHEN any Role_View is generated, THE Collaboration_System SHALL recursively disclose only fields present in the allowlist for the selected role and disclosure phase and shall reject generation when an unallowlisted nested value would be exposed.
8. WHERE P1 is enabled, IF two Role_Views claim the same Contract_Hash but contain conflicting values for one Envelope field, THEN THE Collaboration_System SHALL classify at least one Role_View as invalid.
9. WHERE P1 is enabled, WHEN an allowlist is resolved for Requirement 3.7, THE Collaboration_System SHALL resolve the allowlist from the versioned allowlist definition identified by view_type, view_version, and disclosure phase, and SHALL treat that versioned definition as the only allowlist truth source.
10. WHERE P1 is enabled, WHEN an allowlist entry is added, removed, or modified, THE Collaboration_System SHALL publish a higher view_version for the affected view_type and SHALL record the allowlist definition hash in the View_Manifest.
11. WHERE P1 is enabled, IF a Role_View references a view_version that has no registered allowlist definition, THEN THE Collaboration_System SHALL reject Role_View generation with a Structured_Reason and SHALL classify any verdict bound to that Role_View as invalid.

### Requirement 4: P1 Blind-first verdict 与 Reveal 顺序

**User Story:** 作为 Reviewer，我希望先依据契约和代码事实形成独立判定，再读取实现者说明，以便测量并降低叙事锚定效应。

#### Acceptance Criteria

1. WHERE P1 is enabled, WHILE no Blind_First_Pass_Verdict is sealed, THE Collaboration_System SHALL keep Implementer_Notes, prior reviewer verdicts, reviewer drafts, confidence statements, and suggested review focus unavailable to the Reviewer Session.
2. WHERE P1 is enabled, WHEN a Reviewer submits a Blind_First_Pass_Verdict, THE Collaboration_System SHALL record verdict_id, phase, contract binding, View_Manifest hash, Workspace_Snapshot identity, available reviewer identity, clause decisions, findings, overall decision, submission time, and attestation.

### Requirement 5: P1 Session 独立性与 profile 政策

**User Story:** 作为发布责任人，我希望独立审核要求具有可验证的会话边界，以便实现者不能在同一会话中批准自身改动。

> **独立性的常规解法是"新开一个会话"**：Requirements 5.1 与 5.9 要求的是不同 **Session**，不是不同 Agent 产品或不同模型族。同一个 Agent 产品开一个新会话即产生不同 session_id，因此单 Agent 独立开发者的常规路径是"会话 A 实现 → 新会话 B 盲评 → apply"。不同 agent_id 或不同 model family 仅在 P3 Requirement 10.4 显式配置时才要求。
>
> **`solo` 政策只服务于 session marker 不可用的环境**：当 Agent 或 IDE 无法暴露可区分的 session marker 时，Requirement 5.2 会判定 `unproven_independence`，`task_apply` 将永久被拒且没有合法出路。Requirements 5.12–5.17 定义的 Independence_Policy 把豁免实现在**前件**（该 profile 是否要求 Independent_Review），而不是实现在后件（未证明的独立性能否满足条款）——后者会直接废掉 Requirement 1.5 与设计 Property 5。`solo` 不是给单 Agent 的默认便利。

#### Acceptance Criteria

1. WHERE P1 is enabled and P3 is not enabled, WHEN a task requires Independent_Review, THE Collaboration_System SHALL record every available Implementer and Reviewer session marker and require different session markers before apply.
2. WHERE P1 is enabled, IF different Implementer and Reviewer sessions cannot be demonstrated, THEN THE Collaboration_System SHALL assign `unproven_independence` to the verdict and prevent the verdict from satisfying an independent-review clause.
3. WHERE P1 is enabled, WHEN a `high_risk` profile is evaluated, THE Collaboration_System SHALL require an independent Tester verdict in addition to the Reviewer verdict.
4. WHERE P1 is enabled, WHEN a profile is selected, THE Collaboration_System SHALL apply the required fields, default roles, Evidence set, and gate policy defined for `research`, `design`, `code_change`, `high_risk`, or `review`.
5. WHERE P1 is enabled, IF a profile-required Reviewer or Tester verdict is absent, THEN THE Apply_Gate SHALL fail closed, return a structured missing-verdict reason, and preserve the pre-request task state.
6. WHERE P1 is enabled, WHEN the `research` profile is evaluated, THE Collaboration_System SHALL require one sealed Reviewer Blind_First_Pass_Verdict covering source traceability and declared uncertainty, SHALL require Independent_Review, and SHALL require no executable test Evidence.
7. WHERE P1 is enabled, WHEN the `design` profile is evaluated, THE Collaboration_System SHALL require one sealed Reviewer Blind_First_Pass_Verdict covering objective, non-goals, interfaces, risks, and rollback, SHALL require Independent_Review, and SHALL require no independent Tester verdict.
8. WHERE P1 is enabled, WHEN the `code_change` profile is evaluated, THE Collaboration_System SHALL require one sealed Reviewer Blind_First_Pass_Verdict, current-snapshot Evidence for every executable Blocking_Clause, and Independent_Review, and SHALL require no independent Tester verdict unless an Envelope clause names a Tester Verifier.
9. WHERE P1 is enabled, WHEN the `high_risk` profile is evaluated, THE Collaboration_System SHALL require one sealed Reviewer Blind_First_Pass_Verdict and one independent Tester verdict, SHALL require Independent_Review for both verdicts, and SHALL require the Reviewer Session, the Tester Session, and the Implementer Session to be three different Sessions.
10. WHERE P1 is enabled, WHEN the `review` profile is evaluated, THE Collaboration_System SHALL require one sealed Reviewer Blind_First_Pass_Verdict submitted before the Reveal_Event and SHALL require Independent_Review.
11. WHERE P1 is enabled, WHEN Requirement 1.5 or Requirement 8.3 evaluates a profile-required verdict or a profile-required Independent_Review, THE Collaboration_System SHALL resolve the requirement from the Profile_Policy_Matrix defined in Requirements 5.6 through 5.10 and SHALL reject evaluation with a Structured_Reason when the Envelope declares a profile absent from that matrix.
12. WHERE P1 is enabled, WHEN Requirement 1.5 or Requirement 8.3 determines whether a task profile requires Independent_Review, THE Collaboration_System SHALL resolve that determination from the Profile_Policy_Matrix defined in Requirements 5.6 through 5.10 together with the effective Independence_Policy, SHALL treat this resolution as the Independent_Review part of the Requirement 5.11 resolution, and SHALL treat the profile as not requiring Independent_Review while the effective Independence_Policy value is `solo`, so that the Requirement 1.5 precondition evaluates to false.
13. WHERE P1 is enabled, WHEN an Independence_Policy value is set or changed, THE Collaboration_System SHALL persist the value in the Daemon-owned configuration store that holds the Stage_Toggle values defined in Requirement 13.11, SHALL apply the default value `required` when no value is recorded, SHALL exclude single-request parameters and client-declared identity fields from setting the value, and SHALL record the actor Peer_Identity and the Authoritative_Clock time of the change as an auditable action.
14. WHERE P1 is enabled, IF an Independence_Policy value of `solo` is requested for a task whose Envelope profile is `high_risk`, THEN THE Collaboration_System SHALL reject the requested policy change or the requested evaluation with a Structured_Reason identifying `solo` as prohibited for the `high_risk` profile and SHALL preserve the previous Independence_Policy value.
15. WHERE P1 is enabled, WHILE the effective Independence_Policy value is `solo`, WHEN a gate decision is appended, THE Collaboration_System SHALL record that Independent_Review was waived by policy together with the effective Independence_Policy value, SHALL describe the outcome as a policy waiver rather than as proven independence, and SHALL keep the `unproven_independence` marker assigned by Requirement 5.2 on the affected verdict.
16. WHERE P1 is enabled, WHILE the effective Independence_Policy value is `solo`, THE Collaboration_System SHALL continue to require the Blind_First_Pass_Verdict sealing and Reveal_Event ordering defined in Requirement 1.4, the Evidence freshness for every Blocking_Clause defined in Requirement 1.8, and the scope closure defined in Requirement 1.6.
17. WHERE P1 is enabled, WHEN the effective Independence_Policy value changes from `solo` to `required`, THE Collaboration_System SHALL treat every gate decision produced while `solo` was effective as not reusable and SHALL require re-evaluation of the affected task under the current Independence_Policy, consistent with the Stage_Toggle treatment in Requirement 13.16.

### Requirement 14: 跨平台 daemon 与多会话并行协作

**User Story:** 作为同时运行多个 Agent 会话的开发者，我希望 Windows、macOS 与 Linux 都以同一套 daemon 协作模式工作，以便并行读写不再因数据库锁竞争互相阻塞，也不必退化成单会话串行接力。

> **实现基线**：当前 daemon 服务端仅在 Unix 编译（`server.rs` 的 `#![cfg(unix)]`），Windows 不启动 daemon，且 `_validate_owned_path` 在非 Unix 平台跳过 UID ACL；Windows 命名管道端点、自动唤起与 Degraded_Mode 分级尚未实现，现有能力只有 `server/daemon_client.py` 的只读 SQL 直连回退。本需求描述的是需要补齐的目标能力，不表示已实现。

#### Acceptance Criteria

1. THE Collaboration_System SHALL expose the same collaboration RPC method set through the Daemon on Linux, macOS, and Windows, and SHALL treat a platform on which the Daemon does not start as not supporting the collaboration capabilities of this document.
2. WHERE the host platform is Windows, THE Daemon SHALL accept client connections over a named pipe Daemon_Endpoint.
3. WHERE the host platform is Linux or macOS, THE Daemon SHALL accept client connections over a Unix domain socket Daemon_Endpoint owned by the invoking user and restricted to file mode 0660.
4. WHEN a Session performs an Envelope publication, verdict submission, Reveal_Event, Evidence append, gate evaluation, or Protected_Mutation, THE Collaboration_System SHALL route the operation through the Daemon_Endpoint of the host platform.
5. WHEN a client connection is accepted, THE Daemon SHALL derive Peer_Identity solely from the operating-system Peer_Credential of that connection and SHALL exclude client-declared identity fields, free-text names, and request-body identity values from every authorization decision.
6. WHEN a Protected_Mutation is requested, THE Daemon SHALL apply the mutation through one serialization point located inside the Daemon process, and THE Collaboration_System SHALL expose no second serialization point for Protected_Mutation.
7. WHEN SQLite serializes a write transaction at any stage from P0 through P4, THE Collaboration_System SHALL treat the SQLite write lock only as transaction mutual exclusion and SHALL exclude the SQLite write lock from authorization, ownership, Lease, and Independent_Review decisions.
8. WHERE the host platform is macOS, THE Daemon SHALL derive Peer_Identity from the Peer_Credential UID and GID only and SHALL exclude process id from Peer_Identity, because `LOCAL_PEERCRED` provides no process id.
9. WHERE the host platform is Windows, WHEN a workspace-owned path is validated, THE Daemon SHALL compare the named pipe peer access token SID with the registered workspace owner SID, SHALL reject a mismatch with a Structured_Reason, and SHALL apply this comparison to every path validation that the Unix build protects with a UID ACL.
10. WHERE the host platform is Windows, WHEN a client supplies a canonical payload through the `canonical_bytes_b64` parameter path instead of descriptor passing, THE Daemon SHALL verify the payload size bound and the declared content digest before use and SHALL reject a mismatch with a Structured_Reason.
11. THE Daemon SHALL provide the Authoritative_Clock from the Daemon process clock and SHALL use the Authoritative_Clock for Lease acquisition and expiry, Blind_First_Pass_Verdict and Reveal_Event ordering, Evidence production time, Attestation issuance time, and gate decision time.
12. WHEN a client-supplied timestamp is received, THE Daemon SHALL record the client timestamp as reference metadata and SHALL exclude the client timestamp from Lease expiry evaluation and from verdict-before-reveal ordering.
13. WHEN an Attestation is required for a verdict or an Evidence record, THE Daemon SHALL issue the Attestation from the connection Peer_Credential and the Authoritative_Clock, SHALL bind the Attestation to the Identity, record identifier, View_Manifest hash, Contract_Hash, and validity window, and SHALL reject client-issued Attestations as authorization input.
14. WHEN two or more Sessions concurrently submit well-formed read and write requests for the same workspace, THE Daemon SHALL queue the write requests at the serialization point, complete every well-formed request within the configured request timeout, and return no database-lock error for a request that completes inside that timeout.
15. WHEN two gate evaluations run concurrently, THE Daemon SHALL evaluate each gate against its own Gate_Snapshot, Current_Envelope binding, and Evidence set, and SHALL exclude uncommitted intermediate state of one evaluation from the snapshot and conclusion of the other evaluation.
16. WHEN a gate evaluation requires an expensive Verifier, THE Daemon SHALL execute the Verifier outside the SQLite write transaction and SHALL commit only immutable records and the state transition inside the transaction.
17. WHEN Envelope publication, verdict submission, Reveal_Event, or gate triggering is exposed to users, THE Collaboration_System SHALL expose the operation as a CLI write command routed through the Daemon and SHALL expose Role_View retrieval, Evidence query, Freshness_Status query, and gate decision query as read-only MCP tools.
18. WHERE the host platform is Windows, WHEN the Daemon creates the named pipe Daemon_Endpoint, THE Daemon SHALL derive the pipe name from the owner user SID in the form `\\.\pipe\callwarden-<user-sid>`, SHALL apply a security descriptor that grants connect and read/write access to the owner SID and optionally to the local administrators group, and SHALL grant no access to any other SID, so that the endpoint access scope equals the Unix domain socket owner plus mode 0660 semantics required by Requirement 14.3.
19. WHERE the host platform is Windows, WHILE the Daemon is listening on the named pipe Daemon_Endpoint, THE Daemon SHALL maintain at least two named pipe instances, SHALL create one replacement instance before serving each accepted connection, and SHALL accept every well-formed client connection request issued between two accept operations without returning a pipe-busy or endpoint-absent error.
20. EXCEPT WHERE the versioned MVP_Transport_Profile in Requirements 14.40–14.48 is explicitly selected, THE Collaboration_System SHALL implement the Daemon_Endpoint only as a Unix domain socket on Linux and macOS and as a named pipe on Windows, and SHALL expose no listening TCP port and no local HTTPS endpoint for collaboration RPC, because the operating system provides no Peer_Credential for a TCP connection and Requirement 14.5 could not hold for such an endpoint.
21. WHERE the host platform is Windows, THE Collaboration_System SHALL exclude AF_UNIX sockets from the accepted Daemon_Endpoint implementations, because the Windows AF_UNIX implementation provides no Peer_Credential and therefore cannot satisfy Requirement 14.5.
22. WHEN a client cannot connect to the Daemon_Endpoint, THE Collaboration_System SHALL attempt to start the Daemon, SHALL retry the connection with exponential backoff inside a bounded wait window whose configured default value is 10 seconds measured on the client clock, and SHALL continue the original request over the established connection when a retry succeeds inside that window.
23. WHEN two or more Sessions trigger Daemon auto-start concurrently for the same user endpoint, THE Collaboration_System SHALL acquire a cross-process mutual exclusion primitive before starting a Daemon process, using a named mutex on Windows and a file lock on Linux and macOS, SHALL allow at most one running Daemon process per user Daemon_Endpoint, and SHALL create no second Protected_Mutation serialization point beyond the one required by Requirement 14.6.

Automated negative acceptance SHALL cover non-loopback bind, malformed/oversized requests, stale/wrong-authority manifest, worker failure and governance mutation, client SQLite fallback, request_id conflict, and unknown-as-available registry rows.

### Requirement 15: 三角色治理与任务交接协议

**User Story:** 作为跨多个 Agent 会话协同的开发者，我希望每个任务在 Executor、Reviewer 与 Adjudicator 三个固定治理角色间以可验证的 `task.next_action` 派工和结构化 handoff 交接，以便无论最终回复是否为自由文本，都可以确定性地得到下一合法动作，并保证每笔领料、评审查证与裁决都可追溯到独立身份。

> **实现基线和阶段门禁**：本需求描述的是分阶段待落地能力，不表示已实现。设计细节见 `docs/design/cw-role-handoff-task-loop.md`（cw-task-loop/v1）。公开 capability 复用现有 `StageToggleStore` 之外新增 `task_loop_public` authority 与 `task_loop_capability_promotion_events`；在 0A–0C 能力权限修订与 gate 接入通过 preflight 前，public discovery 和所有已知 public RPC 一律返回 `E_TASK_LOOP_CAPABILITY_DISABLED`。`verdict.submit`、`reveal.submit`、`evidence.append`、`gate.decide` 与 `task_loop.*` 的写路径只在原生 daemon handler + 负向测试 → MCP/CLI 转发 → 拒绝旧兜底 → 移除旧公开写路径的顺序完成后才可标为可用。本需求不改变现有 `task.claim/report/apply/close` 的权威门禁，也不增加 SQLite fallback。

#### Acceptance Criteria

1. THE Collaboration_System SHALL define exactly three governance roles for the task loop — `executor`、`reviewer` 与 `adjudicator` — SHALL bind a chat window to one role and one agent instance, and SHALL NOT allow a window to switch freely among the three roles.
2. THE Collaboration_System SHALL treat the existing runtime roles `planner`、`implementer`、`tester`、`evidence`、`independent_reviewer` as RuntimeRole compatibility values SHALL map them to either `executor` or `reviewer`, and SHALL NOT create additional governance roles from them.
3. WHEN a task-loop governance decision is evaluated, THE Collaboration_System SHALL produce one deterministic decision from `READY`、`WAITING`、`BLOCKED`、`COMPLETE` and one action from `CLAIM`、`REVIEW`、`ADJUDICATE`、`REVISE`、`WAIT`、`NONE`, driven by task status, step→Role Contract binding, dependencies, parent/child close gates, lease, and persisted verdict/evidence/gate projections, rather than by constructing from free-text responses.
4. WHEN a claimable current step or unresolved failed-step remediation exists, THE `task.next_action` SHALL return `READY/CLAIM` with `next_role=executor`, SHALL derive the role solely from the single current bound Role Contract for that step, and WHEN an unresolved `failed` step exists SHALL return its precise `fix_defect`/remediation step as the only claimable target regardless of the `step_index` of later steps.
5. WHEN a task is in `review` with no valid persisted verdict and no unresolved `failed` step, THE `task.next_action` SHALL return `READY/REVIEW` targeting a new and independent `reviewer` instance/session.
6. WHEN a Reviewer submits an effective `BLOCKED` verdict, THE Daemon SHALL atomically return the original task to `in_progress`, append a single provenance-bound `fix_defect` step binding `remediation_of_step_id`、source verdict id、structured findings and source handoff event/request id, and SHALL return `READY/REVISE` to the Executor; THE Reviewer SHALL deliver findings and a read-only `revision_hint` only and SHALL NOT obtain Executor revision authority, create remediation children, or rewrite historical verdicts.
7. WHEN a Reviewer submits an effective `PASS` verdict and all step, subtask, Evidence Gate and lease conditions hold, THE `task.next_action` SHALL return `READY/ADJUDICATE` targeting a new independent `adjudicator` instance/session; THE result SHALL NOT be equivalent to already being applied or closed; WHEN the Adjudicator does not accept, it SHALL return `READY/REVISE` with specific return findings to the Executor.
8. WHEN all terminal gates hold and the task is closed, THE `task.next_action` SHALL return `COMPLETE/NONE`; THE `READY/CLAIM` routing SHALL point only to `executor`, and handoff to the Reviewer SHALL be produced only after the Executor actually reports the step.
9. WHEN any contract is missing, inconsistent, multi-versioned, unhashable, or non-unique step→Role Contract binding is encountered, or the workspace authority is unavailable or mismatched, THE `task.next_action` SHALL fail closed to `BLOCKED/NONE` with `E_TASK_NOT_FOUND_OR_UNAUTHORIZED`, `E_WORKSPACE_AUTHORITY_UNAVAILABLE` or `E_WORKSPACE_AUTHORITY_MISMATCH` as applicable, and SHALL NOT guess a default Executor role or fall back to active workspace.
10. THE Collaboration_System SHALL expose the `task.next_action` as a strictly read-only operation that SHOULD NOT activate a workspace, create a lease, write a task event, or update `task_steps`, and SHALL query only via the daemon/authority and SHALL NOT read SQLite directly.
11. WHEN a structured handoff is committed, THE Daemon SHALL persist a `handoff_event_id`、source/target role、`outcome`、request_id, bind source step、Task Contract triplet、Role Contract triplet、reason、identity and Authoritative_Clock, and SHALL validate the source Role Contract `handoff_to` without generating a verdict, acquiring a lease, or treating the target agent as already claimed.
12. WHEN a canonical first `task.report` request carries any reserved handoff field — `handoff`、`target_role`、`target_agent`、`source_role`、`handoff_reason`、`required_new_instance`、`required_new_session` or `handoff_contract` — THE Daemon SHALL reject it before any task-domain query or write with `E_HANDOFF_REQUIRES_TASK_HANDOFF`, SHALL perform zero domain writes, and SHALL NOT implicitly convert or fall back to the legacy `open` status; THE `task.report` response summary SHALL NOT claim a handoff and SHALL fix `handoff` to `null`.
13. WHEN the `task_handoff_v1` capability is not yet enabled, THE `task.report` SHALL have no handoff semantics; after discovery of `task_handoff_v1`, clients SHALL route handoff via `task.handoff` and pass the stable error unchanged to callers still misusing `task.report`.
14. WHEN a Reviewer verdict is recorded, THE Daemon SHALL append it to the append-only `task_verdict_events` ledger via native `verdict.submit` at the Protected Mutation serialization point, binding Canonical Task Envelope, current step Role Contract triplet, snapshot, real identity, reviewer lease/fencing and Authoritative_Clock; THE Collaboration_System SHALL expose no second write path and SHALL NOT treat a derived `task.events` notification as a verdict truth source.
15. WHERE v1 new Reviewer verdicts are written, THE Collaboration_System SHALL accept only `pass` or `block` as `overall`, SHALL read-only map history as `approved→pass`, `needs_changes`/`request_changes`/`rejected→block`, `unclear`/`abstain→UNVERIFIED`, and SHALL NOT rewrite existing append-only payloads; THE resulting `BLOCKED` and `UNVERIFIED` SHALL be derived decisions rather than new `overall` write values.
16. WHEN a verdict or Evidence is evaluated, THE Collaboration_System SHALL derive freshness and validity only from valid persisted Gate projections — matching Task Contract and Role Contract triplets, step binding, Gate Snapshot, valid attestation/identity, verdict phase and amendment chain — and SHALL fail closed on stale revision, stale snapshot, invalid/revoked attestation, non-independent identity, conflicting amendment or unknown freshness.
17. WHEN a `failed` step is reported, THE Daemon SHALL mark the current step `failed` and append one `fix_defect` step bound to `remediation_of_step_id=<failed_step_id>`; it SHALL NOT set the original step to `done`, overwrite the failure record via `task.reopen`, manual UPDATE, or a new generic task, and a task SHALL NOT enter `review` while any historical `failed` step has no valid resolution event.
18. WHEN `task.claim` is issued while an unresolved failed step exists, THE Collaboration_System SHALL require an explicit `remediation_step_id` and claim exactly that step in one `TASK_DB_LEDGER` transaction; a missing field, a wrong remediation step, or an attempt to claim a later ordinary step SHALL return `E_REMEDIATION_STEP_REQUIRED` or `E_REMEDIATION_STEP_MISMATCH` without changing task/step/event/lease state.
19. WHEN the Executor completes a remediation, THE Collaboration_System SHALL require a protected `task.step.resolve` (or equivalent unique daemon mutation) to append one immutable resolution event instead of modifying `task_steps.status`; THE resolution event SHALL record `failed_step_id`、`remediation_step_id`、`outcome='resolved'`、evidence path and hash、capture id、identity and Authoritative_Clock, and SHALL leave the original failed row's status/result/hash unchanged; a task enters `review` only when no pending step exists and every historical failed step has a valid resolution event.
20. THE Collaboration_System SHALL maintain an append-only `task_operation_ledger` as the authoritative operation/dedup ledger for v1 task-domain mutations scoped to `task.create`、`task.contract_set`、`task.claim`、`task.report`、`task.handoff`、`task.apply`、`task.close`、`lease.acquire`、`lease.renew`（含 alias `lease.extend` 规范化）、`lease.release`、`verdict.submit`、`reveal.submit`、`evidence.append` 与 `gate.decide`, and SHALL key each entry by `(workspace_instance_id, method, request_id)` with a canonical params hash bound to a frozen `params_canonicalization_version`.
21. WHEN a `TASK_DB_LEDGER` mutation is deduplicated, THE Daemon SHALL recompute the incoming canonical params hash using the previously saved rules version; an identical hash SHALL replay the saved result without appending events, and a different hash SHALL return `E_REQUEST_ID_REUSE_MISMATCH` as the priority response; same-request replay SHALL NOT re-run the domain validation.
22. WHEN a domain handler runs under the task-loop wrapper, THE Collaboration_System SHALL require it to call `apply_domain(tx)` with a non-`Clone` `TaskDomainTx` and a frozen `FrozenAuthorityInput`, SHALL require it to return a closed, typed `DomainOutcome` — `CommitSuccess`、`CommitDeterministicError` or `RollbackInfrastructureError` — and SHALL reject classification by error string; success SHALL commit domain writes and ledger result in the same transaction, deterministic error SHALL roll back to a `SAVEPOINT task_domain_callback` and keep a replayable ledger error, and infrastructure error SHALL roll back domain, ledger, and outer transaction.
23. WHEN a designated mutation gate is required, THE Daemon SHALL acquire a workspace-keyed `CapabilityMutationGate` before opening any authority-store or task-DB write transaction and hold it until all related transactions commit or roll back; THE global lock order SHALL be frozen as `CapabilityMutationGate → Capability Authority store transaction → task-DB transaction`, and no path SHALL hold a DB transaction while waiting for the gate or acquire the authority-store lock while holding a task-DB transaction.
24. WHEN a `task_loop.public_promote` control-plane promotion is requested for the public capability, THE Collaboration_System SHALL require a real registered control-plane authority identity, valid space-scoped `Task_Loop_Publication_Authority` id/revision/fencing/validity, Internal permit fingerprint, task-4 evidence, schema fingerprint, runtime binary hash and daemon generation, SHALL commit the full audit event before installing the in-memory Public permit, SHALL distinguish `durable_authorization` from `permit_installation`, and SHALL NOT auto-recover a public permit from historical events.
25. WHEN a public capability mutates state, THE Daemon SHALL revalidate the permit binding (Capability Authority id/revision/fencing/validity, evidence validity, schema/rules fingerprint, runtime binary hash, daemon generation) inside the mutation gate with the final recheck before domain commit; authority unreadable SHALL fail closed to `E_CAPABILITY_AUTHORITY_UNAVAILABLE`, and any mismatch or revocation SHALL clear the in-memory permit and return `E_TASK_LOOP_CAPABILITY_REVOKED` through the deterministic-error savepoint path.
26. WHEN any transport parser (HTTP, Named Pipe, UDS) encounters duplicate JSON keys, THE raw parser SHALL return `E_DUPLICATE_JSON_KEY` and SHALL NOT enter dedup/dispatch; client-supplied `duplicate_keys_checked` or provenance fields SHALL be treated as ordinary unknown/restricted fields that cannot construct a `StrictParsedEnvelope`, and routes SHALL fail closed.
27. WHEN a transport request is parsed, THE Collaboration_System SHALL construct a private, non-serializable `StrictParsedEnvelope` containing `(workspace_instance_id, canonical_method, request_id, params, invocation_class)`, where `invocation_class` is the private enum `ExternalTransport` or `InternalValidation`; HTTP、Named Pipe、UDS strict parsers SHALL construct only `ExternalTransport`, client requests SHALL NOT be able to submit validation markers, and only the private in-process validation API shall use `InternalValidation`.
28. THE Collaboration_System SHALL provide a discoverable `$cw-task-loop` skill entry (`.agents/skills/cw-task-loop/SKILL.md`) that SHALL read AGENTS.md、the frozen design and `cw task next-action --json`, print the derived role card verbatim without claiming steps, switching identity, modifying task state, or substituting for lease validation, SHALL require a new independent review/adjudicate window for those actions, and SHALL re-query after every report or verdict instead of trusting the Agent's final natural-language summary.
29. THE Collaboration_System SHALL bind the Task Contract and Role Contract separately and hash them separately to avoid the semantic ambiguity of a single `contract_hash`, SHALL derive role assignment from a correct single current step→Role Contract binding, SHALL reject claim when the Role Contract or binding hash is missing or mismatched with `BLOCKED/NONE`, and SHALL derive the task logical `workspace_id` from the immutable `task_workspace_bindings` rather than from the active workspace or mutable `active_task_id`; historical task, step, Role Contract or verdict lacking a unique task→workspace binding SHALL be shown as `UNVERIFIED`.
30. WHEN a `reviewer_blocked` handoff is committed, THE Daemon SHALL append the `fix_defect`, the handoff event, and the `review→in_progress` transition in one transaction, SHALL read the latest valid `block` verdict from the same Reviewer identity, SHALL require at least one structured finding, and SHALL bind the source step/verdict/findings/handoff request into the `fix_defect.result`; repeated rounds SHALL append new handoff/fix_defect records without updating old steps, events, or verdicts.
31. THE Collaboration_System SHALL treat a `review` entrance as permitted only with no pending step and a valid resolution for every historical failed step; WHEN that precondition fails, `task.next_action` SHALL keep the task `in_progress` and return `BLOCKED/REVISE` targeting the Executor, and SHALL NOT fake a review transition.
32. WHEN a `task.next_action`, `task.handoff`, `task.report` or remediation computes under a workspace authority that cannot be validated by the daemon registry/authority, THE Daemon SHALL return `BLOCKED/NONE` + `E_WORKSPACE_AUTHORITY_UNAVAILABLE` and SHALL NOT use the active workspace to backfill.
33. Automated negative and concurrency acceptance SHALL cover: daemon-unavailable fail-closed verdict/reveal/evidence/gate submission with unchanged table and task-event row counts, `E_HANDOFF_REQUIRES_TASK_HANDOFF` zero writes, request_id reuse mismatch, duplicate JSON key handling, remediation step claim enforcement, no-`fix_defect`-child for `BLOCKED`, proof-bound `CapabilityMutationGate` lock ordering under concurrent invalidation, no client SQLite fallback, and no default-to-`pass` mapping for ambiguous legacy verdicts.
34. Persistence acceptance SHALL verify that every governance write (handoff, verdict, resolution, lease, gate decision) is append-only, bound to Task/Role Contract triplets and Authoritative_Clock, idempotent under same request-id replay, replayable under historical canonicalization rules, and independently verifiable across daemon restart without recovering a public permit from historical promotion events.

- 跨类操作按组成部分分级（缺陷修正）：Requirements 14.27–14.30 原先假设一个操作只属于 read_only、Index_Write 或 Governance_Write 之一，而 `task_report_step` 单个入口同时刷新文件状态与符号变更记录（Index_Write）并运行 Completion_Gate 判定与追加 Evidence（Governance_Write），因此该入口在 Degraded_Mode 下行为未定义。Glossary 新增 Mixed_Class_Operation；Requirement 14.34 把分级粒度定为组成部分而非整个入口；Requirement 14.35 让 Index_Write 组成部分按 Requirement 14.29 直连执行、Governance_Write 组成部分按 Requirement 14.30 fail closed；Requirement 14.36 要求 Governance_Write 组成部分被拒时任务与步骤状态保持请求前状态，并返回标识已执行与被拒组成部分的 Structured_Reason；Requirement 14.37 禁止把 Index_Write 组成部分的成功解释为门禁通过，且该情形不产生 Evidence 与 gate decision；Requirement 14.38 要求 daemon 恢复后重新执行时 Index_Write 组成部分幂等、Governance_Write 组成部分在 Requirement 14.6 串行化点与 Requirement 14.11 权威时钟下执行；Requirement 14.39 点名 `task_report_step` 为已知跨类操作实例，并要求新增入口同样按组成部分分类。
- 空 scope 发布期防呆（缺陷修正）：Requirement 7.12 对 `research`/`design`/`review` 的空 Allowed_Edit_Scope 记为 `unscoped` 且仅在 Actual_Changes 为空时算在 scope 内，逻辑完备但缺少发布期提示——`design` 任务通常要产出设计文档，Implementer 若忘记在 step 声明 `target_file`，磁盘改动会在 Completion_Gate 或 Apply_Gate 被硬阻断。Requirement 7.15 在此情形下保持 Requirement 7.12 的接受语义并返回一条非阻断 Structured_Warning，说明当前 scope 为空、任何磁盘文件改动都会导致后续 gate 阻断，并提示声明 `target_file` 或 `target_symbol`；Requirement 7.16 明确该警告不改变接受语义、不阻止发布，且携带稳定警告码与可在 `zh_CN`/`en_US` 解析的 i18n key，与 Requirement 1.12 一致；Requirement 7.17 要求该警告同时出现在发布返回值与 CLI 输出中。Glossary 新增 Structured_Warning 并说明其与 Structured_Reason 的非阻断差异。
- Verifier 撤销改为单条撤销记录 + 查询时派生（缺陷修正）：原 Requirement 6.13 要求 Verifier `trust_status` 变为 `revoked` 时"为每条受影响 Evidence 各追加一条失效事件"，存在两层问题。其一是写放大：一个被广泛引用的 Verifier（如 `pytest-junit`）撤销时需要 O(N) 行写入，在大型仓库上造成 WAL 膨胀与写锁占用。其二是与设计自身原则冲突：设计 §9.2 已确立 `fresh/stale/invalid/superseded` 是查询时派生状态，只有"需要持久化失效原因时"才追加 `evidence_invalidated` 事件，持久化是有条件的，而原 6.13 把逐条追加写成无条件强制，成为该原则的例外。修正后 Requirement 6.13 只要求追加**一条** Verifier_Revocation_Record，Evidence 的 `invalid` 由该记录与 Evidence 的 Verifier 三元组 `(name, version, config_hash)` 匹配在查询时派生，回归 §9.2 的派生原则并消除 O(N) 写放大。Requirement 6.20 定义撤销记录的必需字段（Verifier 三元组、撤销原因、发起者身份、按 Requirement 14.11 Authoritative_Clock 记录的撤销时间）并要求不可变、只追加，保证可审计。Requirement 6.21 保证派生确定性：同一 Evidence 与同一撤销记录集合派生出的 Freshness_Status 恒定，且撤销派生的 `invalid` 仍服从 Requirement 6.15 的 `invalid` > `superseded` > `stale` > `fresh` 优先级。Requirement 6.22 保留时点可重算性：gate decision 记录所用 Evidence 的 Verifier 三元组与 Authoritative_Clock 判定时间，与撤销记录的撤销时间共同回答"该 Evidence 在那次判定时刻是否已被撤销"，因此撤销时间早于或晚于某次判定都可事后重算。Requirement 6.23 明确撤销不修改任何既有 Evidence payload，Requirement 1.7 的追加性不受影响。Requirement 6.6 本身不变：Requirement 6.24 明确单条 Evidence 因 payload 校验失败等个体原因失效时仍追加个体失效事件，被取消的只是"撤销 Verifier 时必须逐条写"。Glossary 新增 Verifier_Revocation_Record。
- Attestation 撤销改为单条撤销记录 + 查询时派生，并区分撤销模式（缺陷修正）：Requirement 6.13 与 6.20–6.24 已把 P1 的 Verifier 撤销改为"只追加一条 Verifier_Revocation_Record + 查询时按三元组派生 `invalid`"，但原 Requirement 10.10 对 P3 的 Attestation issuer/签名密钥撤销仍要求"为每条受影响记录各追加一条失效事件"，存在两个问题。其一是同构的写放大：daemon 签名密钥签发过大量 verdict 与 Evidence 的 Attestation，逐条写同样是 O(N) 行写入，造成 WAL 膨胀与写锁占用。其二是机制口径分裂：同属"第三方凭证/签名失效"范畴，P1 走查询时派生而 P3 走物化，两套做法并存。修正后 Requirement 10.10 只要求追加**一条** Attestation_Revocation_Record，受影响 verdict 与 Evidence 的 `invalid` 由该记录与记录所携 Attestation 的 issuer 标识、签名密钥标识匹配在查询时派生，与 Requirements 6.13、6.20–6.24 的 Verifier 撤销对称。Requirement 10.11 定义撤销记录的必需字段（issuer 标识、签名密钥标识、Revocation_Mode、撤销原因、发起者身份、按 Requirement 14.11 Authoritative_Clock 记录的撤销时间）并要求不可变、只追加。
  直接对称照搬还会引入一个新的严重问题：原 10.10 是一刀切，撤销即全部 `invalid`，不分签发时间。但 Attestation 密钥撤销有两种性质完全不同的原因，因此撤销模式不是可选增强，而是查询时派生能否正确落地的**前提**——派生函数必须靠它决定是否比较签发时间。Glossary 新增 Revocation_Mode 与 Attestation_Revocation_Record。Requirement 10.12 规定 Revocation_Mode 必填且无默认值，缺少该字段的撤销请求以 Structured_Reason 拒绝且不追加任何撤销记录：默认成 `rotated` 会让密钥泄露被当成轮换处理，从而放过轮换时点之前用泄露密钥伪造的历史记录；默认成 `compromised` 会让每次例行轮换把整个历史账本判为 `invalid`，所有 verdict 需重新评审，实际上使密钥轮换不可行。Requirement 10.13 定义 `compromised` 语义：忽略 Attestation 签发时间，该 issuer/key 签发的全部记录判为 `invalid`，因为泄露状态下无法区分哪些签发是伪造的。Requirement 10.14 定义 `rotated` 语义：仅当 Attestation 签发时间晚于撤销记录的撤销时间时判为 `invalid`，签发时间早于或等于撤销时间的记录保持原有有效性判定不变，从而保住例行轮换的历史有效性。
  Requirement 10.15 保证派生确定性：同一记录与同一撤销记录集合重复派生结果恒定，且撤销派生出的 `invalid` 与 Requirement 10.9 列举的其他 Attestation 校验失败原因（自签、issuer 不符、绑定或签名失败、越出有效窗口）取同一 `invalid` 结论，不产生第二种状态。Requirement 10.16 保留时点可重算性，与 Requirement 6.22 对称：gate decision 记录其所依赖每条 verdict/Evidence 的 Attestation issuer 标识、签名密钥标识与 Attestation 签发时间，以及按 Authoritative_Clock 记录的判定时间，把这些与匹配撤销记录的撤销时间和 Revocation_Mode 比较即可回答"该记录在那次判定时刻是否已因撤销而失效"。Requirement 10.17 明确撤销不修改任何既有 verdict/Evidence payload，逐字节保留，Requirement 1.7 的追加性不受影响。Requirement 10.18 明确个体失效仍走事件：单条 verdict/Evidence 因自身原因失效（如 Attestation 绑定校验失败、payload 校验失败）时仍按 Requirement 6.6 的个体失效事件机制处理，被取消的只是"issuer/key 撤销时必须逐条写"。Requirements 10.8、10.9 的校验规则与 Requirements 14.13、14.31 对降级产物的 Attestation 判定均保持不变，本次修正只改变撤销失效的记录方式与时间语义。
- 独立审核豁免落在前件而非后件（缺陷修正）：Requirements 5.1 与 5.9 要求的是不同 **Session** 而非不同 Agent，因此单 Agent 独立开发者的常规解法是新开一个会话（不同 session_id 即满足独立性），不同 agent_id 或 model family 仅在 P3 Requirement 10.4 显式配置时才要求。真正的死锁场景是 Agent 或 IDE 无法暴露可区分的 session marker：此时 Requirement 5.2 判定 `unproven_independence`，`task_apply` 被永久拒绝且没有任何合法出路。修正采用的口径是把豁免实现在**前件**——改"该 profile 是否要求 Independent_Review"，而不是改"未证明的独立性能否满足条款"；后者会直接废掉 Requirement 1.5 与设计 Property 5。Glossary 新增 Independence_Policy（默认 `required`，非默认 `solo`）。Requirement 5.12 规定 Requirement 1.5 与 8.3 判定"profile 是否要求 Independent_Review"时由 Profile_Policy_Matrix（Requirements 5.6–5.10）与 Independence_Policy 共同解析，`solo` 生效时该 profile 不再要求 Independent_Review，Requirement 1.5 的前件为假。Requirement 5.13 把 Independence_Policy 持久化在 Daemon 拥有的配置存储中（与 Requirement 13.11 的 Stage_Toggle 同源），默认 `required`，禁止由单次请求参数或客户端自报字段设置，并记录发起者 Peer_Identity 与 Authoritative_Clock 时间，使开启豁免本身成为可审计动作而非静默绕过。Requirement 5.14 对 `high_risk` profile 禁用 `solo`，请求时以 Structured_Reason 拒绝并保留原政策值。Requirement 5.15 要求 `solo` 生效时 gate decision 记录"独立审核按政策豁免"及当时的 Independence_Policy 取值，不得表述为"独立性已证明"，verdict 仍按 Requirement 5.2 携带 `unproven_independence`。Requirement 5.16 明确 `solo` 不放宽任何其他门禁：Requirement 1.4 的封存与 reveal 顺序、Requirement 1.8 的 Blocking_Clause Evidence freshness、Requirement 1.6 的 scope 封闭性一律照常要求。Requirement 5.17 规定 `solo` 期间产生的 gate decision 在政策改回 `required` 后不可复用，必须在当前政策下重新评估，与 Requirement 13.16 对 Stage_Toggle 的处理一致。
